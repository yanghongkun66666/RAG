# AgentX RAG 学习版开发计划

这份计划不是给有很多项目经验的人写的，而是给“后端基础一般、想靠项目实战系统学习 RAG”的初学者写的。

你现在的目标，不是一下子复刻完整 AgentX，也不是一开始就去做最复杂的 HyDE、RRF、版本市场、Agent 绑定。

你真正要做的是：

- 先做一个你自己能看懂、能跑通、能持续迭代的学习版 RAG
- 先把最基础的 RAG 主链做出来
- 再一点点逼近 AgentX 的完整效果
- 每做完一个功能点，就停下来 review、总结、提交 git

这份计划只聚焦：

- RAG 基础能力

暂时不纳入主线：

- Agent 设计
- Widget
- Agent 绑定知识库

这些可以等你把 RAG 主线吃透之后再做。

---

## 1. 你最终要做成什么

你最终要做的是一个“学习版 RAG 管理系统”。

它不需要一开始就很漂亮，但要能帮助你验证每一步功能。

建议总入口先固定成下面 5 个页面：

1. 知识库管理
2. 文件处理实验台
3. 语料实验台
4. 检索实验台
5. 问答实验台

后面如果你进入版本化阶段，再加：

6. 版本管理台

这样做的好处是：

- 每个功能点都有落脚页
- 你不会写了一堆后端接口却没地方验证
- 你能把“开发、验证、学习、总结”放在同一个系统里

## 1.1 你的学习项目到底应该放在哪里

这个问题很重要，我直接给你结论：

- `不要` 直接在 `AgentX-Newest` 里面把学习版一路改下去
- `不要` 在 `AgentX-Newest` 里面再套一个新的独立 git 仓库
- `最推荐` 的做法是：和 `AgentX-Newest` 并列，新开一个学习项目文件夹

推荐目录结构：

```text
D:\Java\Projects\Finished Projects\
├─ AgentX-Newest
└─ AgentX-RAG-Learn
```

这里两边的职责要分清楚：

- `AgentX-Newest`：参考项目，只读、只查、只对照
- `AgentX-RAG-Learn`：你的学习项目，真正开发、提交、review、合并都在这里完成

为什么我推荐“并列”而不是“就在当前目录开发”：

1. 你自己的学习代码会更干净
2. git 历史不会和 AgentX 混在一起
3. 你随时都还能参考 AgentX 的代码和文档
4. 以后你回头看，会很清楚哪些是“官方实现”，哪些是“我自己重做的实现”

所以你的实际工作方式应该是：

1. 在 `AgentX-RAG-Learn` 开发
2. 在 `AgentX-Newest` 查实现
3. 每次做功能前，先看 AgentX 对应章节文档，再看关键代码
4. 然后回到自己的项目里，用“最小可运行版本”重新实现

## 1.2 这份计划怎么体现“参考 AgentX”

这份计划不是让你“离开 AgentX 自己瞎做”，而是让你：

- `以 AgentX 为参考目标`
- `以学习版为实现载体`

也就是说，你不是直接复制 AgentX，而是按下面这个顺序学：

1. 先看 AgentX 这一块最终长什么样
2. 再理解它为什么要这么分层
3. 然后回到你自己的学习版里，先做一个更简单的版本
4. 等你掌握基础后，再逐渐往 AgentX 靠近

所以后面每一个模块，你都要做两件事：

- `参考 AgentX`
- `自己重做`

两者缺一不可。

## 2. 整体学习路线

这条路线分三层：

### 第一层：P0 主线基础

先把最基础、最容易建立信心的功能做出来。

目标是先跑通：

知识库 -> 文件 -> 语料 -> 向量 -> 检索 -> 简单问答

### 第二层：P1 主线进阶

在主线跑通以后，再做：

- 异步处理
- 更多文件类型
- 检索增强

### 第三层：P2 扩展能力

最后再做：

- 版本管理
- 发布 / 安装 / 市场

这部分是“更像 AgentX 产品能力”的扩展，不是你的第一学习重点。

## 3. 开发总原则

你在整个学习过程中，都要固定遵守下面这些原则。

### 3.1 永远先做最小可运行版本

例如：

- 先做 txt，不要一开始做 PDF
- 先做同步处理，不要一开始做 MQ
- 先做向量检索，不要一开始做混合检索
- 先做同步问答，不要一开始做流式问答

原因很简单：

- 你现在最缺的不是“高级功能”
- 你最缺的是“对完整主链的感觉”

### 3.2 每次只做一个功能点

不要一个分支里同时做：

- 文件上传
- 语料查看
- 向量化优化

一定要拆开。

因为你是学习驱动，不是赶工驱动。

功能点太多，你最后既不知道哪里写错了，也不知道自己到底学会了什么。

### 3.3 每次做完必须验证

不要出现这种情况：

- 代码写完了
- 没测
- 直接切下一个功能

你必须做到：

- 每一步都能看到结果
- 每一步都知道数据库怎么变了
- 每一步都知道哪里可能失败

### 3.4 每次做完都要 review

你已经明确说了，想每次开发完一个分支以后自己 review，再学习实现思路，再提交 git。

这个习惯非常好，必须保留。

因为对你来说：

- review 不是收尾动作
- review 本身就是学习动作

### 3.5 注释必须写成“教学式注释”

你现在不是给一个成熟团队冲刺交付，而是在做“自己的实战教材”。

所以注释必须这样写：

- 类注释：这个类负责什么
- 方法注释：这个方法解决什么问题
- 关键代码块注释：为什么这样写

不要写这种没价值的注释：

- 给变量赋值
- 循环列表
- 调用接口

这种注释对学习没有帮助。

### 3.6 要学会 Vibe Coding，但不能变成“随便让 AI 写”

你说你想熟悉 `vibe coding`，这件事可以做，但一定要理解清楚。

对你来说，`vibe coding` 不是：

- 想到什么就让 AI 写什么
- 不看代码就直接接受
- 不验证功能就继续往下堆

对你来说，更合适的做法应该是：

- 你先说清楚目标
- 让 Codex 先帮你搭最小版本
- 你再去读代码、跑功能、看数据库变化
- 看不懂的地方继续追问，直到你能自己讲出来

也就是说，你要练的是：

- `先让 AI 帮你加速产出`
- `再靠 review 和验证把理解补回来`

这才是适合初学者的 `vibe coding`。

### 3.7 要开始练 Harness Engineering

你还提到要开始应用 `harness engineering`。  
在这份学习计划里，我把它落成下面这套非常具体的动作。

你每做一个功能点，都不要只给 Codex 一句“帮我实现”。  
你要先给出一个最小的“开发约束框架”，也就是你的 `harness`。

每次开工前，固定写这 6 项：

1. 这次只做什么
2. 这次明确不做什么
3. 输入是什么
4. 输出是什么
5. 完成标准是什么
6. 我准备怎么验证

例如你做最小 RAG 闭环时，可以这样写：

```md
本次功能：手工输入文本 -> 切分 -> 向量化 -> 检索
本次不做：文件上传、MQ、问答生成
输入：一段手工输入文本，一个用户问题
输出：topK 命中的语料段
完成标准：问题能命中最相关的片段
验证方式：页面输入文本和问题，检查返回结果和数据库记录
```

这就是你给 AI 的“护栏”。

你要记住一句话：

- `vibe coding` 解决的是“产出速度”
- `harness engineering` 解决的是“不要跑偏”

这两个东西要一起练，不能只练前者。

### 3.8 每个分支都要有自己的最小 Harness

从现在开始，你每个分支必须至少带上 4 个固定产物：

1. 一张任务卡
2. 一份输入输出说明
3. 一份验证清单
4. 一份 review 结论

也就是说，你不是只提交代码。

你每个功能点最后都要形成下面这套学习闭环：

任务卡 -> 让 AI 实现 -> 自己验证 -> 自己 review -> 提交 git -> 写学习总结

如果你坚持这样做，你会比单纯“看教程”成长快很多。

### 3.9 任何时候都不要脱离 AgentX 参考系

你自己的学习版可以简化，但不能完全脱离 AgentX。

因为你最后的目标不是做一个随便的 RAG demo，而是：

- 先做出简化版
- 再逐步逼近 AgentX 的真实链路

所以每个模块都要固定问自己 3 个问题：

1. AgentX 这一块真实是怎么做的
2. 我现在为什么先做简化版
3. 我后面准备怎么往 AgentX 靠

### P0-1 工程外壳与最小管理台

**优先级：最高**

**推荐分支名：**

- `learn/00-shell`

**这一阶段你要做什么：**

- 搭建学习版项目
- 跑通数据库连接
- 跑通 pgvector
- 跑通 RabbitMQ 连接
- 做统一异常返回
- 做统一日志输出
- 搭最小管理台菜单

**为什么先做这个：**

因为你后面所有功能都要落在这个壳子里。

如果没有这个壳子，你后面每做一个功能，都得重新补环境和页面入口，会很乱。

**实现步骤：**

1. 创建学习版项目。
2. 配好数据库和基础表初始化。
3. 配好 RabbitMQ 连接。
4. 做一个统一返回结构。
5. 做一个统一异常处理器。
6. 做一个统一日志输出格式。
7. 做最小管理台首页。
8. 在首页上放 5 个功能入口占位页。

**完成标准：**

- 项目可以启动
- 数据库可以连接
- pgvector 可以初始化
- RabbitMQ 可以连接
- 页面可以进入
- 5 个入口页哪怕是空白页也能打开

**这一阶段你要学会什么：**

- 一个项目怎么先搭出“长期可扩展的学习骨架”
- 为什么基础设施要先稳定

---

### P0-2 最小 RAG 闭环

**优先级：最高**

**推荐分支名：**

- `learn/01-basic-rag-text`

**这一阶段你要做什么：**

先不要上传文件。

先做最小能力：

- 手工输入一段文本
- 把文本切成几个片段
- 为片段做 embedding
- 存到向量库
- 输入问题后做向量检索

**为什么第二步就做这个：**

因为这才是 RAG 的真正核心。

你必须先对下面这几个概念有感觉：

- 原始文本
- 语料片段
- 向量
- 检索结果

如果这一层没吃透，后面上传文件、MQ、流式问答都会变成“只是在搬代码”。

**实现步骤：**

1. 做一个“手工输入文本”的页面。
2. 输入文本后，按最简单规则切分。
3. 把切分结果保存下来。
4. 对每个片段做 embedding。
5. 存入向量库。
6. 做一个问题输入框。
7. 根据问题做向量检索。
8. 展示 topK 结果。

**完成标准：**

- 输入一段文本后可以存下来
- 输入问题后能召回最相关片段
- 你能解释“为什么这几段被召回”

**这一阶段你要学会什么：**

- RAG 最核心的最小闭环到底长什么样

---

### P0-3 简单 RAG 问答

**优先级：最高**

**推荐分支名：**

- `learn/02-simple-qa`

**这一阶段你要做什么：**

在最小检索闭环的基础上，加一个“检索后回答”。

先做同步回答，不做流式。

**固定流程：**

问题 -> 检索 -> 拼接 context -> 调模型 -> 返回答案

**为什么现在做：**

因为你要尽快明白一件事：

- RAG 不是“直接把问题丢给模型”
- RAG 是“先找资料，再让模型参考资料回答”

**实现步骤：**

1. 保留 P0-2 的检索能力。
2. 检索到 topK 语料片段。
3. 把这些片段拼成上下文。
4. 构造一个最简单的提示词。
5. 把问题和上下文一起发给模型。
6. 返回答案。
7. 页面同时展示：
   - 原问题
   - 命中的语料
   - 最终答案

**完成标准：**

- 能看到命中的语料
- 能看到基于语料生成的答案
- 你能清楚知道“资料是怎么喂给模型的”

**这一阶段你要学会什么：**

- RAG 问答的最基础工作方式

### P0-4 知识库、文件、语料三层模型

**优先级：最高**

**推荐分支名：**

- `learn/03-dataset-file-corpus`

**这一阶段你要做什么：**

把之前的“纯文本 demo”升级成真正的知识库结构。

固定为三层：

- 知识库
- 文件
- 语料

第一批表固定为：

- `dataset`
- `file_detail`
- `document_unit`
- `vector_store`

**为什么这一步非常关键：**

因为这是你理解 AgentX RAG 设计的分水岭。

你会开始明白：

- 为什么不能只留向量库
- 为什么需要 `document_unit`
- 为什么知识库和文件不能混成一张表

**实现步骤：**

1. 新建知识库表和知识库管理接口。
2. 引入文件表 `file_detail`。
3. 引入语料表 `document_unit`。
4. 调整之前的最小 demo：
   - 文本先挂到某个知识库下
   - 再挂到某个文件下
   - 再切成多个语料段
5. 向量索引只保存检索相关数据。

**完成标准：**

- 你能创建知识库
- 知识库下能看到文件
- 文件下能看到语料
- 检索仍然能工作
- 你能解释每张表负责什么

**这一阶段你要学会什么：**

- AgentX 里最核心的数据分层思想

### P0-5 文件上传与文本文件入库

**优先级：高**

**推荐分支名：**

- `learn/04-upload-txt-md`

**这一阶段你要做什么：**

开始支持真正的文件上传。

但文件类型先固定顺序：

1. `txt`
2. `md`

暂时不要做：

- pdf
- word
- 异步 MQ

这一阶段先允许同步处理，只要把主链跑通就行。

**为什么这样安排：**

因为 txt 和 md 最容易帮助你理解：

- 文件内容怎么读出来
- 怎么切分
- 怎么进入语料层

而不会一下子被 OCR 和复杂文件格式拖垮。

**实现步骤：**

1. 做文件上传接口。
2. 文件上传后先保存到本地或文件存储。
3. 在 `file_detail` 里记录元信息。
4. 读取 txt 内容。
5. 把 txt 切分成多个语料段。
6. 写入 `document_unit`。
7. 做向量化。
8. 同样支持 md 文件。

**完成标准：**

- 上传 txt 后能看到文件记录
- 能看到切分后的语料段
- 检索和问答都能使用这份文件
- md 也能跑通基本链路

**这一阶段你要学会什么：**

- 文件进入知识库的完整主流程

---

### P0-6 语料可视化与人工修正

**优先级：高**

**推荐分支名：**

- `learn/05-corpus-view-edit`

**这一阶段你要做什么：**

做文件下的语料查看和修改。

功能固定为：

- 语料分页查看
- 关键词搜索
- 单条语料编辑
- 单条语料删除
- 编辑后重新向量化

**为什么这一步一定要做：**

因为这一步会帮你真正理解：

- `document_unit` 不是过渡表
- 它是标准语料层

这也是 AgentX 很重要的设计点。

**实现步骤：**

1. 做“查看文件下所有语料”的页面。
2. 支持分页。
3. 支持关键词搜索。
4. 支持编辑单条语料内容。
5. 编辑后把对应向量重建。
6. 支持删除单条语料。
7. 删除后同步处理对应向量。

**完成标准：**

- 你能在页面看到某个文件的所有语料
- 改完某条语料后，检索结果真的变了
- 删除一条语料后，检索不会再命中它

**这一阶段你要学会什么：**

- 为什么业务语料层和向量索引层必须分开

### P1-1 异步处理链路

**优先级：高**

**推荐分支名：**

- `learn/06-async-pipeline`

**这一阶段你要做什么：**

把同步处理拆成两段异步链路。

固定为：

- 第一段：文件处理 / 文本解析 -> 产出 `document_unit`
- 第二段：语料向量化 -> 写入 `vector_store`

同时补：

- 文件状态
- 文件进度

**为什么放在这里做：**

因为你只有在已经理解同步版本之后，才能真正看懂 MQ 是在解什么问题。

如果一开始就做异步，你会只记住“发消息、消费消息”，但不知道为什么这样设计。

**实现步骤：**

1. 给 `file_detail` 增加处理状态字段。
2. 增加 OCR/处理进度字段。
3. 增加向量化进度字段。
4. 第一段 MQ 负责生成 `document_unit`。
5. 第二段 MQ 负责向量化。
6. 页面轮询处理进度。
7. 页面展示：
   - 已上传
   - 处理中
   - 完成
   - 失败

**完成标准：**

- 上传文件后不是同步卡住
- 页面能看到状态变化
- 两段消息都能独立工作

**这一阶段你要学会什么：**

- AgentX 为什么把文件处理拆成两段总线

---

### P1-2 文件类型扩展

**优先级：高**

**推荐分支名：**

- `learn/07-word-txt`
- `learn/08-markdown-enhance`
- `learn/09-pdf-ocr`

**固定顺序：**

1. Word / txt
2. Markdown 结构化处理
3. PDF OCR

**为什么必须按这个顺序：**

因为难度是逐步增加的：

- 文本类最容易
- Markdown 有结构化增强
- PDF 最复杂，要处理 OCR 和多页

**实现步骤：**

#### 第一步：Word / txt

- 读出文件文本
- 做句子切分
- 写语料
- 向量化

#### 第二步：Markdown

- 先做原文结构切分
- 再做增强文本
- 再做向量化

#### 第三步：PDF

- 按页处理
- OCR 提取文本
- 写入语料
- 向量化

**完成标准：**

- 每支持一种文件类型，都能完成：
  - 上传
  - 处理
  - 看语料
  - 检索
  - 问答

**这一阶段你要学会什么：**

- 不同文件类型为什么不能共用完全一样的处理策略

### P1-3 检索增强

**优先级：中高**

**推荐分支名：**

- `learn/10-keyword-search`
- `learn/11-hybrid-search`
- `learn/12-rrf`
- `learn/13-rerank`
- `learn/14-hyde`
- `learn/15-query-expansion`

**固定顺序：**

1. 关键词检索
2. 混合检索
3. RRF
4. rerank
5. HyDE
6. 查询扩展

**为什么这样安排：**

因为这些能力是层层叠加的。

你必须先理解：

- 向量检索不够的地方是什么

然后再看：

- 关键词检索如何补
- 混合检索如何合并
- RRF 如何融合
- rerank 如何重排
- HyDE 如何改写问题
- 查询扩展如何补上下文

**实现步骤：**

每加一层，都要做两件事：

1. 加功能
2. 做对比实验

对比实验至少记录：

- 原问题
- 改造前结果
- 改造后结果
- 你自己的判断

**完成标准：**

- 你能解释每个增强模块解决什么问题
- 你能用实际结果说明它有没有价值

**这一阶段你要学会什么：**

- RAG 检索为什么不是“只做向量搜索就够了”

### P1-4 流式问答

**优先级：中高**

**推荐分支名：**

- `learn/16-stream-chat`

**这一阶段你要做什么：**

把同步问答升级成流式问答。

页面要能展示：

- 检索开始
- 检索结果
- 回答生成中
- 回答结束

**为什么最后做：**

因为流式问答的难点不是“流”本身，而是：

- 你前面的检索和问答基础已经稳定

如果前面没稳定，流式只会把调试难度放大。

**实现步骤：**

1. 保留同步问答逻辑。
2. 改成流式返回。
3. 把问答过程拆阶段消息。
4. 前端逐段显示。
5. 页面展示检索命中的文件和片段。

**完成标准：**

- 你能看到回答是一段段出来的
- 你能看到检索过程
- 不是只有最终答案

**这一阶段你要学会什么：**

- AgentX 为什么把 RAG 问答做成“可观察过程”

## 8. 每个分支的固定开发流程

你后面每一个功能点，都固定按这个流程来。

### 第零步：先做 AgentX 对照卡

在真正开始写代码前，你先不要急着实现。

你要先回答下面 4 个问题：

1. AgentX 这一块的入口在哪里
2. AgentX 这一块的核心表有哪些
3. AgentX 这一块最小主链是什么
4. 我这次准备先简化掉哪些东西

这张“对照卡”不用写很长，但必须有。

因为它能保证你不是脱离参考系乱做。

### 第一步：先写任务卡

每次开分支，先写一张很短的任务卡。

只写这 5 项：

1. 目标
2. 输入
3. 输出
4. 完成标准
5. 我准备怎么验证

不要上来直接写代码。

### 第二步：给 Codex 一个最小 Harness

你以后不要只说一句：

- “帮我实现这个功能”

你要固定给出下面这类输入：

```md
主开发项目：AgentX-RAG-Learn
参考项目：AgentX-Newest

这次分支：learn/01-basic-rag-text

本次只做：
- 手工输入文本
- 文本切分
- 向量化
- 向量检索

本次不做：
- 文件上传
- MQ
- 问答生成

请先参考 AgentX 对应实现思路，但只修改我的学习项目。
请先输出任务卡，再实现，再给我验证步骤。
代码必须带教学式注释。
```

这就是你和 Codex 协作时最基础的 `harness`。

### 第三步：再写代码

写代码时必须带教学式注释。

固定要求：

- 类上写类注释
- 方法上写方法注释
- 关键逻辑前写原因注释

### 第四步：先自己验证

至少验证 4 件事：

1. 接口是否通
2. 页面是否通
3. 数据库是否写对
4. 错误路径是否合理

### 第五步：自己 review

每个分支固定回答这 5 个问题：

1. 这个模块入口在哪
2. 主流程是什么
3. 数据从哪来，到哪去
4. 失败会发生什么
5. 我一周后还能不能看懂

### 第六步：再提交 git

建议 commit 格式固定为：

- `feat(rag-learn): 完成 xx 模块`
- `fix(rag-learn): 修复 xx 问题`

## 11. 你开发时最容易犯的错

这里提前提醒你几个高概率问题。

### 11.1 一上来做太复杂

比如：

- 一上来就做 PDF
- 一上来就做混合检索
- 一上来就做流式

这会让你很快失去控制感。

### 11.2 只盯接口，不看数据库

RAG 这类系统如果不看数据库变化，很容易变成“接口能返回就以为对了”。

你必须养成习惯：

- 每做完一步，都看表数据怎么变了

### 11.3 只关注成功路径

你必须主动看失败情况：

- 文件为空怎么办
- embedding 失败怎么办
- 检索不到结果怎么办
- 语料编辑后向量重建失败怎么办

### 11.4 注释写得太敷衍

你后面最宝贵的学习资料，不只是代码，还有你自己写下来的解释。

所以注释一定要认真写。

## 14. GitHub 仓库怎么建

这一节按“企业最低标准”来写，但我会尽量用最容易照做的方式说。

你现在是一个人开发，也建议从一开始就按稍微正规一点的方式来做。

### 14.1 仓库最小标准

建议你一开始就固定下面这些规则：

- 仓库默认建成 `Private`
- 默认主分支叫 `main`
- 不直接在 `main` 上开发
- 每个功能点一个分支
- 所有功能都通过 PR 合并回 `main`

这 5 条已经是非常好的起步标准了。

### 14.2 GitHub 上新建仓库的步骤

1. 登录 GitHub。
2. 点击右上角 `New repository`。
3. 仓库名称建议简单清楚，比如：
   - `rag-learning-lab`
   - `agentx-rag-learning`
4. 选择 `Private`。
5. 勾选：
   - `Add a README file`
   - `Add .gitignore`
6. `.gitignore` 选择你项目对应的技术栈。
7. 创建仓库。

### 14.3 本地项目第一次推到 GitHub

如果你本地已经有项目，第一次推送可以按下面步骤做：

```bash
git init
git branch -M main
git remote add origin <你的仓库地址>
git add .
git commit -m "chore: 初始化学习版 RAG 项目"
git push -u origin main
```

### 14.4 仓库创建后建议立刻补的东西

至少补下面 3 个文件：

1. `README.md`
   写清楚这个项目是干什么的、怎么启动、当前做到哪一步。

2. `docs/` 或 `docs_rag/`
   用来放你的学习计划、阶段总结、问题记录。

3. `.env.example`
   把需要的环境变量列出来，但不要把真实密钥提交上去。

### 14.5 主分支保护建议

如果你想更像企业一点，可以去 GitHub 仓库设置里打开分支保护。

位置大致是：

- `Settings`
- `Branches`
- `Add rule`
- 针对 `main`

建议最少打开：

- 不允许直接 push 到 `main`
- 必须通过 Pull Request 合并

如果现在只有你一个人开发，先不要强制：

- 必须别人审批

因为你自己一个人时会比较麻烦。

以后有同伴了，再加“至少 1 个 Review”就可以。

## 15. 代码怎么 review

你已经说了，每个分支做完后想先自己 review 再提交。

这个习惯非常好，我建议你把它变成固定流程，而不是“想到才 review”。

### 15.1 review 的目标是什么

对你来说，review 不是挑别人毛病，而是确认：

- 我有没有真的做对
- 我有没有真的看懂
- 我下周还能不能接着改

### 15.2 自我 review 的顺序

每次 review 都按这个顺序来。

#### 第一步：先跑一遍功能

不要先看代码。

先自己点一遍页面，或者调一遍接口，确认功能真的能用。

因为很多问题不是“代码看不出来”，而是“运行时一试就露出来了”。

#### 第二步：再看自己改了哪些文件

先看：

```bash
git status
git diff --stat
git diff
```

你要先搞清楚：

- 这次到底改了哪些地方
- 有没有改到不该改的文件
- 有没有带上调试代码

#### 第三步：按主链路读一遍

RAG 功能最好按这条线 review：

- 页面入口
- 接口
- service
- 数据库
- 返回结果

也就是问自己：

- 用户点了哪里
- 请求发到哪里
- 后端谁处理
- 写了哪些表
- 页面最后看到什么

#### 第四步：查失败路径

你一定要问：

- 输入为空怎么办
- 检索不到结果怎么办
- 向量化失败怎么办
- 文件上传失败怎么办

很多初学者只看成功路径，这是很容易吃亏的。

#### 第五步：查可读性

最后看：

- 注释够不够
- 方法是不是太长
- 类是不是职责太多
- 命名是不是自己一周后还能看懂

### 15.3 每次 review 固定问自己的 10 个问题

建议你把下面这 10 个问题直接存成模板，每次照着答。

1. 这个功能的入口在哪？
2. 主流程是什么？
3. 数据从哪来？
4. 数据最后写到哪去？
5. 页面上最后展示的内容是从哪个接口来的？
6. 如果输入不合法，会发生什么？
7. 如果后端出错，会发生什么？
8. 有没有调试代码没删？
9. 有没有写清楚关键注释？
10. 我一周后还能不能重新讲清楚这段代码？

### 15.4 review 时重点看的 8 类问题

以后你 review 自己的代码，可以重点看这 8 类：

1. 功能有没有真的跑通
2. 有没有多改文件
3. 有没有硬编码配置
4. 有没有把密钥、密码提交进去
5. 异常有没有处理
6. 数据库写入有没有漏字段
7. 页面和接口字段名是不是对得上
8. 注释是不是足够清楚

## 16. 怎么提交、怎么提 PR、怎么合并

这一节你要养成习惯，因为这就是以后真正企业开发的基本动作。

### 16.1 最低标准：不要直接改 main

哪怕现在只有你一个人，也不要直接在 `main` 上写代码。

固定流程是：

`main`
-> 开功能分支
-> 开发
-> 自测
-> review
-> 提 PR
-> 合并

### 16.2 每次做功能时的标准 Git 流程

假设你现在要做“最小 RAG 闭环”，流程建议固定成这样：

```bash
git checkout main
git pull
git checkout -b learn/01-basic-rag-text
```

然后开始开发。

开发过程中可以反复看状态：

```bash
git status
git diff
```

写完后：

```bash
git add .
git commit -m "feat(rag-learn): 完成最小RAG闭环"
git push -u origin learn/01-basic-rag-text
```

### 16.3 commit 信息怎么写

你现在最适合用最简单的规范提交方式。

建议固定用这几种：

- `feat`: 新功能
- `fix`: 修 bug
- `docs`: 改文档
- `refactor`: 重构
- `chore`: 杂项

举例：

- `feat(rag-learn): 完成最小RAG闭环`
- `feat(rag-learn): 增加txt文件上传`
- `fix(rag-learn): 修复语料编辑后未重建向量的问题`
- `docs(rag-learn): 补充P0阶段学习笔记`

### 16.4 Pull Request 怎么提

把分支 push 上去以后，在 GitHub 上发起 Pull Request。

建议你每个 PR 只做一个功能点，不要太大。

PR 标题建议直接沿用 commit 语义，比如：

- `feat(rag-learn): 完成最小RAG闭环`

PR 描述建议固定写下面这些内容：

#### 这次做了什么

比如：

- 增加手工输入文本
- 增加文本切分
- 增加向量检索

#### 怎么验证

比如：

- 输入一段文本
- 提问一个问题
- 检查是否命中正确片段

#### 改了哪些地方

比如：

- 后端接口
- 数据表
- 管理台页面

#### 还有什么没做

比如：

- 目前只支持手工文本
- 还不支持文件上传

### 16.5 一个初学者也能用的 PR 模板

你可以把下面这段内容每次复制到 PR 描述里：

```md
## 本次目标

-

## 本次完成

-

## 验证方式

-

## 风险和不足

-

## 学到的东西

-
```

这个模板很适合你，因为它能逼着你边做边总结。

### 16.6 合并前最后检查什么

在点击合并前，固定再看一次下面这些点：

1. 功能真的能跑
2. 文档有没有同步更新
3. 有没有调试代码没删
4. 有没有无关文件一起提交
5. 有没有把 `.env`、密钥、账号密码提交上去

### 16.7 合并方式怎么选

如果你每个分支只做一个功能点，建议默认用：

- `Squash and merge`

原因是：

- 历史更干净
- 一个 PR 最后就是一个提交
- 以后回头看学习记录更清楚

### 16.8 合并后的收尾动作

每次合并后，固定做下面几步：

```bash
git checkout main
git pull
git branch -d learn/01-basic-rag-text
```

## 19. 只严格按开发计划做，能不能完成整个 RAG 链路

结论先说：

- `可以`

但前提是你要正确理解“严格按计划做”到底是什么意思。

这里的“严格按计划做”，不是：

- 只看这份计划标题
- 不看 AgentX
- 不做验证
- 不做 review

这里真正的意思是：

1. 按模块顺序推进，不跳步骤
2. 每个模块都做最小可运行版本
3. 每个模块都对照 AgentX 理解真实目标
4. 每个模块都做验证和回顾
5. 做完基础版后，再一点点往 AgentX 靠

只要你真按这个方式做，这份计划是足够把整条 RAG 主链跑起来的。

这条链路包括：

- 知识库
- 文件
- 语料
- 向量化
- 检索
- 问答
- 检索增强
- 版本化

也就是说，这份计划不是“只能做 demo”，而是：

- `先做 demo 级的最小版本`
- `再把它逐步推到接近 AgentX 的完整链路`

### 19.1 这份计划不能替代什么

你也要知道，这份计划本身不能替代下面这些动作：

1. 读 AgentX 对应代码
2. 自己跑验证
3. 自己看数据库变化
4. 自己做 review
5. 自己总结为什么要这样设计

所以真正完整的学习闭环是：

开发计划 + AgentX 参考 + 实际编码 + 验证 + review

少任何一个，都会变空。

## 20. 你这个学习计划里，Vibe Coding 和 Harness Engineering 分别怎么落地

最后我把这两个词再用最简单的话收一下，防止你后面理解跑偏。

### 20.1 Vibe Coding 在你这里是什么意思

在你这里，它不是“随便写”。

它真正的意思是：

- 让 Codex 帮你加快搭建速度
- 你自己重点补“理解、验证、review”这三件事

所以你每次都可以放心让 Codex 帮你做：

- 搭目录
- 搭接口
- 补基础页面
- 写最小可运行版本
- 给你解释关键代码

但你不能放弃这几件事：

- 自己读代码
- 自己跑功能
- 自己看数据
- 自己写总结

### 20.2 Harness Engineering 在你这里是什么意思

在你这里，它不是高深理论。

它就是：

- 给 AI 明确边界
- 给开发过程明确验证方式
- 给每个分支留下可复查的过程记录

所以你以后每个分支，至少都要留下：

1. AgentX 对照卡
2. 任务卡
3. Codex 输入模板
4. 验证记录
5. review 记录

这 5 样东西，就是你最基础的开发 Harness。

### 20.3 你最后会得到什么能力

如果你真的按这份计划走到后面，你最后学到的不只是 RAG。

你还会顺便学到：

- 怎么和 AI 协作开发
- 怎么把需求拆成小步
- 怎么给 AI 设边界
- 怎么做基础验证
- 怎么做基础代码 review
- 怎么按企业最低标准提交和合并

这对你后面做任何 AI 项目，都会有帮助。

## 22. 以后你每开发一个功能，具体该怎么操作

这一节非常重要。  
你以后每一个功能点，都尽量按这套顺序走，不要临时想到什么就做什么。

### 22.1 开发一个功能点的标准动作

固定顺序如下：

1. 先看 AgentX 对应文档
2. 再看 AgentX 关键代码
3. 用 `rag-dev-harness` 写 AgentX 对照卡
4. 写任务卡
5. 用 `prompt-enhancer` 或 `meta-prompt-engineering` 把需求补完整
6. 再让 Codex 开始实现
7. 开发后自己验证
8. 用 `review` / `review-java` / `review-diff` 做复盘
9. commit
10. PR
11. 合并
12. 写学习总结

这套动作以后应该变成你的默认肌肉记忆。

### 22.2 每个 skill 分别应该在什么时候用

#### `rag-dev-harness`

这是你以后最常用的 skill。

它负责：

- 固定主项目和参考项目角色
- 生成 AgentX 对照卡
- 生成任务卡
- 生成验证清单
- 生成 review 清单
- 约束每个分支的边界

你以后每开一个新分支，最好都先用它。

#### `prompt-enhancer`

当你的需求表达还比较短、比较口语化的时候用。

例如你只说：

- “帮我做最小 RAG 闭环”

它适合帮你补全成：

- 目标
- 输入
- 输出
- 完成标准
- 实现范围

#### `meta-prompt-engineering`

当你希望给 Codex 一个“更稳、更有护栏”的输入时用。

它特别适合：

- 复杂一点的功能点
- 你怕 AI 跑偏的时候
- 你想把约束写清楚的时候

#### `aim`

当你开始一个阶段、一个模块、甚至一个版本时用。

它帮助你先想清楚：

- 我最终想达到什么结果
- 这个阶段的真正目标是什么

适合在阶段开始前用，不一定每次小改动都用。

#### `problem-statement`

当你发现自己虽然在做功能，但问题本身讲不清楚时用。

例如：

- 到底是“做上传功能”
- 还是“做文件进入语料层的能力”

这个 skill 能帮你把问题说对。

#### `solution-space`

当你已经知道问题是什么，但还在几个实现方案之间犹豫时用。

例如：

- 同步实现还是异步实现
- 先做 txt 还是先做 md
- 是先落语料还是先写向量

#### `review`

这是你每个分支结束后最值得固定使用的 skill。

它负责：

- 检查有没有偏离目标
- 检查有没有做多
- 检查当前实现是不是还算清楚

#### `review-java`

当后端 Java 代码已经开始成型后，用它查：

- 结构问题
- 代码味道
- 分层是否混乱
- 是否容易维护

#### `review-diff`

当你想从“这次改动本身”角度看问题时用。

尤其适合：

- 提交前
- PR 前
- 你怀疑改动太大时

#### `review-code`

这个更像通用审查。

适合在你已经做完一块功能后，再做一轮整体质量检查。

#### `review-security`

后面只要涉及下面这些内容，就值得用：

- 文件上传
- 配置项
- MQ
- 权限
- 外部模型调用
- API 入参校验

#### `review-testing`

当你开始补测试、补验证、补自动检查时用。

#### `tdd`

这个 skill 不是要求你一开始就机械地完全 TDD。

但在下面这些情况特别有价值：

- 你在补检索逻辑
- 你在改切分逻辑
- 你在修 bug
- 你担心回归风险

#### `generate-github-workflow`

后面你的学习项目稳定一些之后，用它给项目补：

- CI
- 自动检查
- 自动测试

#### `setup-pre-commit`

这是非常值得保留的开发体验增强。

它能帮你在提交前自动做一些检查，减少低级错误。

#### `git-guardrails-claude-code`

这个适合企业环境和初学者环境。

它的作用是减少危险 git 操作带来的损失，比如：

- 错误 reset
- 错误删分支
- 错误清理工作区

### 22.3 一个功能点的推荐调用顺序

如果你以后要做一个新功能，推荐用这个顺序：

```text
1. rag-dev-harness
2. prompt-enhancer 或 meta-prompt-engineering
3. Codex 实现
4. review / review-java / review-diff
5. review-security（如果有风险点）
6. review-testing（如果要补测试）
```

不是每次都要把所有 skill 全用上。  
但上面这个顺序是你目前最稳的主线。

## 23. 企业环境下，第一步到底该做什么

如果现在假设你是在企业里接手一个新项目，或者你入职后为了过试用期要开始做一个项目，第一步不是写代码。

### 23.1 企业环境的第一步

第一步永远应该是：

- `先把项目的边界、目标、规范、环境、交付方式搞清楚`

也就是先回答下面这些问题：

1. 这个项目到底要解决什么问题
2. 谁是使用者
3. 这次我要负责哪一块
4. 当前代码仓库在哪里
5. 开发分支规范是什么
6. 提交流程是什么
7. 测试流程是什么
8. 上线流程是什么

如果这些你都没搞清楚，就直接开始写代码，风险会非常高。

### 23.2 如果把这件事落到你当前学习项目里

那你的“企业化第一步”应该是：

1. 新建 `AgentX-RAG-Learn`
2. 初始化 Git 仓库
3. 复制开发计划
4. 建立最小目录结构
5. 明确 `AgentX-Newest` 只是参考项目
6. 创建第一个分支 `learn/00-shell`
7. 写 AgentX 对照卡和任务卡
8. 再开始开发

也就是说，真正的第一步是：

- `先把开发框架搭起来`

而不是：

- `先写第一个 Controller`

### 23.3 企业里最基本的开发规范

你现在至少要养成下面这些最基本的规范：

1. 不直接在 `main` 开发
2. 一个分支只做一件事
3. 改代码前先看上下文
4. 提交前先自测
5. 提交前先 review
6. PR 描述要写清楚
7. 不提交密钥、密码、本地配置
8. 不随便删别人的代码
9. 不随便改分支历史
10. 合并后及时同步主分支

### 23.4 试用期最容易被看重的能力

如果你以后真是在企业里，这些能力往往比“会不会炫技”更重要：

- 能不能把任务拆小
- 能不能按规范提交流程
- 能不能清楚说明自己改了什么
- 能不能自测
- 能不能发现问题并复盘
- 能不能稳定交付，而不是一次写很大一坨

所以你现在这套学习方式，其实很适合拿来练试用期基本功。
